Append-only. Status: Accepted unless noted.

## ADR-001 — Next.js 16 (Turbopack default), no `src/` directory

**Date:** 2026-04-27

**Context:** App scaffolded with `create-next-app` at `/docket/`. Next 16 ships Turbopack as the default for `next dev` and `next build`; `--turbopack` flag is no longer needed. The original Stage 00 plan (Next 15) is retargeted to Next 16. We do not opt into a `src/` folder — feature folders live at the project root.

**Decision:** Stay on Next 16.x. No `src/`. `@/*` alias maps to project root.

**Consequences:** Per `AGENTS.md`, consult `node_modules/next/dist/docs/` before writing route handlers, layouts, or middleware. Several APIs that were sync in training data are now async (`cookies()`, `headers()`, `params`). `middleware.ts` becomes `proxy.ts` in Stage 02.

## ADR-002 — Drizzle ORM, direct Postgres via `DATABASE_URL`

**Date:** 2026-04-27

**Context:** All DB access goes through Drizzle on a single Postgres connection (`DATABASE_URL`). Postgres host is not locked — Supabase, Neon, Railway, RDS all work. Drizzle bypasses PostgREST and any Supabase-specific client.

**Decision:** Use Drizzle + `postgres` (postgres-js) for all DB I/O. RLS still enabled at the DB level (Stage 01) as defense-in-depth.

**Consequences:** No vendor lock-in for the database layer. Migrations are SQL files generated by `drizzle-kit`. `prepare: false` required when connecting through pgbouncer/pooler.

## ADR-003 — Auth.js (NextAuth) v5 + Drizzle adapter, NOT Supabase Auth

**Date:** 2026-04-27

**Context:** The original plan (CLAUDE.md §5) locked Supabase Auth. On review, that would have required `SUPABASE_URL` + `SUPABASE_ANON_KEY` purely to call Supabase's hosted `/auth/v1/*` endpoints — extra coupling for a service that handles only OAuth. Auth.js can do the same with `AUTH_SECRET` + per-provider OAuth client IDs/secrets, storing sessions/users in our own Postgres via the Drizzle adapter.

**Decision:** Use Auth.js v5 with the Drizzle adapter. Sessions, accounts, and users live in our DB. Providers: Google, Apple, Microsoft (SSO-only — no email/password).

**Consequences:** Auth state is in tables we control (easier admin tooling, no second source of truth). Apple SSO still requires an Apple Developer account + Services ID — no shortcut there. Stage 02's plan, written for Supabase Auth, is superseded by this ADR; the Auth.js wiring is what actually ships.

## ADR-004 — Inngest for background jobs

**Date:** 2026-04-27

**Context:** Document extraction, Computer-driven case builds, and email sending all need durable execution beyond a single HTTP request. Options: DB-polled queue (cheap, but reinvents retries), BullMQ (needs a Redis worker process, not Vercel-friendly), Inngest (managed, Vercel-native, idempotent by default).

**Decision:** Inngest. One function per workflow under `server/jobs/`. Functions must be idempotent (natural keys / upserts).

**Consequences:** Adds a third-party dependency, but the alternative (DB poller + worker) costs more engineering for less reliability. Webhook endpoint at `/api/webhooks/inngest` (path centralized in `config/api.routes.ts`).

## ADR-005 — `config/` is for paths and identity only; service-local constants stay with the service

**Date:** 2026-04-27

**Context:** First draft of `config/` included `limits.ts` (revenue split, compute caps, file-size caps) and `copy.ts` (UI strings). User pushed back: "How does revenue belong to limit?" Lumping unrelated constants under `config/` creates a junk drawer.

**Decision:** `config/` holds: app identity (`app.config.ts`), page routes (`app.routes.ts`), API endpoints (`api.routes.ts`), validated env (`env.ts`, `public-env.ts`). Nothing else. Business limits live next to the service that owns them. UI copy co-locates with the component, or in `lib/messages.ts` if shared. Brand/CSS tokens live in `app/globals.css` `@theme`.

**Consequences:** `config/` stays small and obviously-scoped. Adding a new constant requires asking "what service owns this?" instead of dumping into a shared bucket.
